**Public Cloud - AWS
1.AWS
=>개요
- Amazon에서 제공하는 Public Cloud 서비스
- 시스템 운영에 필요한 서비스 일체를 사용할 수 있음
- 다른 Public Cloud에 비해서 서비스 조합이 쉬움: 매년 강화
AWS 와 AWS 외부의 시스템 또는 네트워크를 연동하는 사례가 늘고 있음
- 종량제: 사용한 만큼 지불
- 사용이 쉬움: 웹 브라우저에서 거의 대다수의 설정이 가능
- 서울에 한국 전담팀 상담 창구가 마련되어 있음
AWS 도입을 지원하는 APN(Amazon Partner Network) 기업도 있는데 AWS가 공식적으로 인증하는 최상위 프리미터 컨설팅 파트너는 국내에 3개사(Megazon Cloud, 베스핀 글로벌, GS 네오텍)
- 보안 기준 따르고 있음
한국은 ISMS(한국 정보보호 관리체계) 인증을 취득하여 기준을 준수하고 있음
- 글로벌 확장이 쉬움
가장 많은 데이터 센터를 소유
한국에도 서울에 3개의 az(데이터 센터)을 소유
- 165개 이상의 서비스를 소유
일반적으로 알려진 인프라의 대부분을 제공

=>용어
- Region
AWS의 모든 서비스가 위치하고 있는 물리적인 장소로 전 세계 주요 지역에 위치하고 있으며 Region 안에는 가용 영역(데이터 센터)이 여러 개 존재 할 수 있음
Region이 여러 개인 이유는 가까운 곳에서 접속을 해야 빠른 속도를 낼 수 있고 하나의 Region이 불능 상태가 되더라도 다른 Region에서 서비스를 지속적으로 제공할 수 있기 때문

- AZ(Availability Zone - 가용 영역)
데이터 센터와 유사한 개념
각 가용 영역은 같은 지역 또는 도시라 하더라도 물리적인 위치가 다름
가용 영역에 따라 동일한 서비스라도 비용이 다름
ELB는 같은 Region 안에 여러 가용 영역에 걸쳐있는 서비스에 트래픽 분배가 가능

- Edge Location
AWS의 CDN 서비스인 CloudFront를 위한 캐시 서버
CDN 서비스는 Content Delivery Service의 약자로 컨텐츠를 사용자들이 빠르게 받을 수 있도록 전 세계 곳곳에 위치한 캐시 서버에 복제해주는 서비스
CDN 캐시 서버는 인터넷 트래픽을 효과적으로 처리할 수 있는 지역에 POP(Point-of-Presense)를 구축하는데 CDN 서비스와 사용자가 직접 만나는 곳이라고 해서 Edge 라고 부름
AWS에서는 CloudFront 와 Route53 서비스에서 제공

2.EC2
=>개요
- 컴퓨팅 용량을 제공하는 서비스
- Managed Service가 아님: 서버 와 네트워크 운영은 AWS가 담당하지만 그 이외의 모든 작업은 사용자가 담당
- 클릭한 번으로 최적의 서버 생성
- 장점
바로 사용 가능
여러 가지 선택할 수 있음
생성과 삭제가 편리
- 단점
서버 1대로 구성되어 그다지 변화가 없는 시스템의 경우라면 AWS의 장점을 살릴 수 없음

=>주요 구성
- 인스턴스
AWS 클라우드에 만들어지는 가상 서버
AMI로 같은 구성의 서버를 생성할 수 있음

- AMI: 가상 이미지, 인스턴스를 생성하는 기준

- Key Pair: 인스턴스에 접속할 때 인증을 위해 사용하는 키

- EBS: AWS 클라우드에서 사용할 수 있는 스토리지로 인스턴스의 스토리지로 사용

- 보안 그룹: 가상 방화벽으로 1개 이상의 인스턴스 트래픽을 제한

- Elastic IP: 고정(정적) IPv4 주소

=>요금 체계
- 인스턴스 사용량(가동 시간 * 단가): 정지하고 있는 동안은 과금이 되지 않음

- EBS 요금(용량 * 단가)
저장 용량이 아니고 보유한 용량 단위
인스턴스가 정지되고 있어도 과금

- 통신 요금
아웃바운드 요금만 과금(인터넷으로 나가는 요금만 과금)
리전 단위로 단가는 다름

- 기타 옵션
Elastic IP 서비스를 신청하면 해당 요금이 과금

=>Elastic IP
- EC2에서 기본적으로 제공하는 Public IP는 재시작을 하면 변경됩니다.
- Elastic IP는 고정 IP 서비스 입니다.
- 인스턴스 단위가 아니고 AWS 계정에 연결됩니다.
- 여러 개의 인스턴스와 연결이 가능
- 기본적으로 계정당 1개는 무료이고 추가로 사용하면 요금이 과금됩니다.
- 인스턴스 와 연결할 때는 Elastic IP를 선택한 후 상단의 주소 연결을 클릭해서 인스턴스를 선택

=>키페어 없이 계정 과 비밀번호로 SSH 접속이 가능하도록 설정
- ssh 접속할 때 마다 pem 파일을 이용하는 것이 번거로운 경우 설정
- 계정을 만들어서 해도 되고 기존 계정을 수정해서 사용해도 됩니다.
- /etc/sudoers 파일 과 /etc/ssh/sshd_config 파일을 수정하면 됩니다.
- 설정
유저 생성: sudo adduser 계정

유저 권한 변경
	sudo chmod u+w /etc/sudoers
	sudo vi /etc/sudoers 한 후 계정명=(ALL:ALL) ALL을 추가

SSH 접속 방법 수정
	sudo vi /etc/ssh/sshd_config
		PasswordAuthentication yes
		KbdInteractiveAuthentication yes	

SSH 재시작: sudo service ssh restart

=>보안 그룹
- 보안 그룹은 가상 방화벽 역할을 수행
- 보안 그룹은 인스턴스 앞에서 트래픽을 제어하는 가상 방화벽이고 Network ACL(Access Control List)은 서브 네트워크 앞에서 트래픽을 제어하는 역할
- 인스턴스에 접근하기 전에 앞문의 성격이 Network ACL이고 중문의 성격이 보안 그룹
- Amazon의 VPC에서는 인스턴스에는 5개까지 보안 그룹을 설정할 수 있고 VPC는 2500개 까지 설정 가능
- 동일한 서브 네트워크 안에 있는 인스턴스끼라 다른 보안 그룹 적용 가능
- 인바운드 규칙에 어떤 트래픽을 허용할 것인지 설정
- 보안 그룹을 설정할 때는 허용할 포트 와 IP 범위를 설정
- 자주 사용되는 포트는 이름을 만들어 두었고 IP에서 모든 IP를 허용하고자 할 때는 AnyWhere IPv4 와 AnyWhere IPv6가 있습니다.

=>Load Balancing
- ELB
AWS가 제공하는 Load Balancer

- ELB 종류
ALB
	L7 로드밸런서
	요청되는 명령어의 내용을 보고 판단하기 때문에 대상의 URL 디렉토리 단위로 분배하는 것이 가능
	인스턴스 와 LoadBalancer 사이에 암호화가 가능
	지원 프로토콜: HTTP 와 HTTPS

NLB
	OSI 모형의 전송 계층에서 동작: L4 로드밸런서
	패킷이라고 불리는 단편 데이터 밖에 볼 수 없기 때문에 분배 대상의 IP 주소를 설정
	지원 프로토콜: TCL, TLS
GLB
	AWS 환경으로 들어오고 나가는 네트워크 트래픽을 차세대 방화벽(NGFW), 침입 탐지 및 방지 시스템, 심층 패킷 검사 시스템 같은 서드파티 가상 네트워크 가전 장비들로 쉽고 안전하게 라우팅하고 이 장비들을 관리할 수 있게 해주는 부하 분산 서비스

	기존의 ALB 나 NLB는 사용자의 요청을 애플리케이션 서버로 분산하는데 특화되어 있는데 기업에서 보안을 강화하기 위해서 PaloAlto, Check Point, Fortinet 같은 전문 방화벽 장비를 AWS 환경에 도입할려고 할 때 문제가 발생
		복잡한 라우팅 구조: 트래픽이 반드시 방화벽을 거쳐 나가도록 라우팅 테이블을 이리저리 꼬아서 설정해야 함
		고가용성(HA)의 한계: 특정 방화벽 장비가 죽으면 네트워크 전체가 마비되거나 이를 복구하기 위한 스크립트를 작성해야 함
		스케일링의 어려움: 트래픽이 몰릴 때 방화벽 장비의 개수를 자동으로 늘리거나 줄여야 하는데 매우 까다로움

	이러한 문제를 해결하기 위해서 트래픽의 게이트웨이의 역할을 하면서 동시에 방화벽 장비들을 뒤에 묶어 자동으로 부하를 분산하고 장비가 고장나면 알아서 정상적인 장비로 트래픽을 돌려주기 위한 것이 GLB

=>고가용성 아키텍쳐 설계
- 고가용성(High Availability)
시스템이나 서비스가 전원 장애, 하드웨어 고장, 네트워크 문제, 자연재해 등 어떤 장애 상황에서도 중단되지 않고 지속해서 정상 운영할 수 있는 능력을 의미

장애가 발생해도 성능이 떨어지면 안됨

AWS에서 ELB는 Managed Service 라서 트래픽이 많으면 ELB을 늘리고 트래픽이 적으면 알아서 줄임

AWS에서 고가용성을 구현하기 위해서는 다중 가용 영역과 Auto Scaling을 이용

ELB를 만들 때 최소 2개 이상의 가용 영역을 선택하는 이유가 고가용성 아키텍쳐를 구현하기 위해서

- 가용성 등급

99.9%		: 일반적인 엔터프라이즈 서비스의 기본 수준
99.99%	: 고가용성을 달성했다고 보는 표준적인 수준
99.999%	: 금융권, 의료 시스템, 클라우드 핵심 인프라 수준

=>내결함성(Fault Tolerance)
- 시스템 내의 일부 하드웨어나 소프트웨어에 결함이나 오류가 발생하더라도 시스템 전체가 멈추지 않고 전반적인 기능과 서비스를 정상적으로 계속 유지하려는 능력
- 장애 허용 시스템 또는 장애 감내 시스템이라고 함
- 내결함성을 구현하는 핵심 기술
하드웨어 레벨의 예비 부품
	RAID(디스크 다중화)
	Dual Power Supply

소프트웨어 및 네트워크 레벨의 감지
	Replication: 데이터베이스의 데이터를 실시간으로 동기화된 예비 DB에 복사해 두었다가 메인 DB가 죽으면 바로 이어받는 구조
	에러 핸들링과 서킷 브레이커: 소프트웨어 내부에서 특정 기능에 대한 에러가 반복되면 전체 시스템이 멈추지 않도록 해당 기능으로 가는 길을 잠시 차단하고 현재 점검 중 같은 안내를 띄우고 나머지 기능은 정상 작동하도록 격리시키는 방식

=>Auto Scaling Group 을 이용한 고가용성 아키텍쳐 구현
- Auto Scaling Group
미리 정의한 조건에 따라 EC2 인스턴스의 개수를 자동으로 늘리거나 줄여주는 인스턴스들의 관리 그룹
필요한 이유
	비용 절감: 사용자가 적을 때는 최소의 서버만 켜두고 사용자가 많은 경우 서버를 늘려서 사용한 만큼만 비용을 지불할 수 있음
	내결함성 및 고가용성 보장
	예측 불가능한 트래픽 대응
핵심 설정 값
	최소 크기
	최대 크기
	평상시 원하는 크기
확장 정책: 서버를 늘리고 줄이는 것을 결정하는 규칙
	대상 추적 확장 정책: 가장 많이 사용하는 방식으로 특정 목표 수치를 지정하면 알아서 맞추는 방식
 	단계별 확장 정책: 단계값을 설정해서 추가하거나 줄이는 방식
	예약된 확장 정책: 이벤트 일정을 알고 있을 때 사용
