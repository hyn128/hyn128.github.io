*모니터링: 관측 가능성
=>관측 가능성
- 시스템의 외부 출력 정보 만으로 내부의 상태와 작동 조건을 정확하게 파악할 수 있는지 나타내는 개념
- 핵심 요소
Metrics: CPU 사용량, 메모리, 응답 시간 등 시간에 따른 수치 데이터
Logs: 시스템에서 발생한 이벤트나 에러 메시지의 시간순 기록
Traces: 분산된 서비스 환경에서 하나의 요청이 거쳐간 경로와 처리 과정을 기록, 웹에서 쿠키를 저장하라고 하는 이유 중 하나가 Traces
- 모니터링은 이미 알고 있는 문제의 징후를 감시하는 것으로 보고 관측 가능성은 시스템 내부의 맥락을 파악해서 예측 불가능한 근본 원인을 찾아내는 과정

3)핵심 지표
=>CPU
- CPU Usage: CPU를 얼마나 사용하는가?
- User/System/IO Wait: CPU 사용률 구분
- Load Average: 실행 대기 중인 작업의 평균 수준
- 지속적인 고사용률은 병목 가능성 -> 프로세스 및 요청량 분석 필요
- 관련된 명령어: top, htop, mpstat, vmstat 등

=>Memory
- Total/ Used/ Available/ Free Memory
- Cache/Buffer: Linux가 성능 향상을 위해서 사용하는 메모리
- Swap 사용 여부는 메모리 압박의 중요한 신호
- 메모리 부족은 OOM Killer, 프로세스 종료, 응답 지연으로 이어질 수 있음
- 관련된 명령어: free -h, vmstat, top 등

=>Disk & File System
- Disk Usage: 사용량 - 남은 용량
- Disk I/O: 읽기/쓰기 처리량과 IOPS, I/O Wait 확인
- 용량 부족 현상은 로그 증가, DB 파일, 임시 파일 등에서 발생
- I/O 병목 과 단순 용량 부족을 구분할 수 있음
- 관련 명령어: df -h, du -sh, iostat, lsblk 등

=>Network
- Traffic: 송수신 Bytes 또는 Packets
- Error / Drop: 패킷 손실이나 인터페이스 오류
- Connection: TCP 연결 수, ESTABLISHED, TIME_WAIT 
- Latency: 네트워크 지연 시간
- 명령어: ss, ip -s link, sar -n, ping(ICMP - handshake)

4)모니터링의 4가지 관점
=>Availability: 서비스가 살아있는가?
=>Performance: 얼마나 빠르게 응답하는가?
=>Resources: 자원이 얼마나 사용되는가?
=>Business/Service: 사용자가 실제로 정상적인 서비스를 받고 있는가?

=>CPU 사용률이 20% API 응답 시간이 5초라면 정상이라고 볼 수 없다.

8)Alert 설계 원칙
=>모든 지표에 Alert를 걸지 않음
=>단순 임계치보다는 지속 시간 + 여러 지표를 함께 고려
=>Critical/Warning 등 우선 순위를 구분
=>예: CPU가 90% 넘는 상황이 5분 이상 지속되면 Warning
=>예: Disk가 85%이면 Warning 그리고 95% 이상이면 Critical
=>Alert Fatigue를 줄여서 실제 중요한 알림에 집중

9)장애 대응 프로세스
=>Detect: 이상 징후 탐지
=>Triage: 영향 범위와 심각도 판단
=>Diagnose: Metric/Log/Trace를 이용해서 원인 분석 
=>Mitigate: 서비스 정상화를 위해서 긴급 조치
=>Recover: 정상 상태인지 확인
=>Postmortem: 원인, 대책, 재발 방지책 정리

10)Dashboard 만들 때 고려 사항
=>상단: Service Availability, Error Rate, Response Time
=>중단: CPU/Memory/Disk/Network
=>하단: Process/Container/Kubernetes Pod 상태
=>색상 보다는 한 눈에 이상 징후를 발견할 수 있는 배치가 중요
=>Dashboard는 운영자 관점에서 설계

11)운영 환경에서 자주 발생하는 장애
=>CPU 급증 -> 트래픽 급증/ 트래픽 증가/ 무한 루프 분석
=>Memory 부족 -> Memory Leak / Cache / 프로세스 증가 분석
=>Disk Full -> 로그 폭증 / 임시 파일 / DB 데이터 확인
=>Network 장애 -> 연결 수 / Drop / DNS / Load Balancer 확인 
=>Application 장애 -> Error Rate +  Response Time + Log + Trace를 함께 분석

12)Linux Monitoring 명령
=>top 으로 확인
=>메모리를 확인할 때 free -h 명령을 사용하는데 이 때 free 와 available의 값이 다음
- 실제 메모리 부족 여부는 available을 가지고 판단
- Linux는 남는 메모리를 Cache/Buffer로 적극적으로 사용하기 때문

=>CPU 부하 발생: yes > /dev/null &

=>현재 디스크 상태 확인: df -h
디스크 운영 기중

< 70% 	정상
70~80%	관심
80~90%	Warning
> 90% 	Critical
> 95%	긴급 조치

- 디렉토리 확인
sudo du -sh /home/<MANAGED_USER> 2>/dev/null

- 5M 가 넘는 파일을 확인
sudo find /home/<MANAGED_USER> -type f -size +5M -exec ls -lh {} \;

- 추출한 내용은 관리할 컴퓨터의 /var/log/daily_check 디렉토리에 저장

- 플레이북 파일 생성: monitoring_facts.yml
---

- hosts: all
  vars:
    log_directory: /var/log/daily_check

  tasks:
    - name: Print system info
      ansible.builtin.debug:
        msg:
        - "################ Start #####################"
        - "Date: {{ ansible_facts.date_time.date }} {{ ansible_facts.date_time.time }}" 
        - "HostName: {{ ansible_facts.hostname }}"
        - "OS: {{ ansible_facts.distribution }}"
        - "OS Version: {{ ansible_facts.distribution_version }}"
        - "OS Kernel: {{ ansible_facts.kernel }}"
        - "CPU Cores: {{ ansible_facts.processor_vcpus }}"
        - "Memory: {{ ansible_facts.memory_mb.real }}"
        - "Interfaces: {{ ansible_facts.interfaces }}"
        - "IPv4: {{ ansible_facts.all_ipv4_addresses }}"
        - "Devices: {{ ansible_facts.mounts }}"
        - "################# End #######################" 
      register: result
      become: yes
    - name: Create log directory
      ansible.builtin.file:
        path: "{{ log_directory }}"
        state: directory
      become: yes
    - name: Print logs to log file
      ansible.builtin.shell: |
        echo "{{ item }}" >> "{{ log_directory }}"/system_info.logs
      loop: "{{ result.msg }}"
      become: yes

- 문법 체크: ansible-playbook -i inventory.ini --syntax-check monitoring_facts.yml -K

- 실행 체크: ansible-playbook -i inventory.ini --check monitoring_facts.yml -K

- 실행: ansible-playbook -i inventory.ini monitoring_facts.yml -K

- 출력 내용을 확인해봐도 대고 관리하는 컴퓨터에 접속해서  /var/log/daily_check 디렉토리를 확인해도 됩니다.

=>패키지를 직접 설치해서 명령어로 관리 
- 변수를 위한 파일: vars_packages.yml
---

log_directory: /home/<MANAGED_USER>/logs
packages:
  - dstat
  - sysstat

- 패키지 설치 및 명령 파일: monitoring_system.yml
---

- hosts: all
  vars_files: vars_packages.yml
  become: yes
  
  tasks:
    # 1. 로그 디렉토리 생성 태스크를 가장 먼저 추가하세요
    - name: Create log directory
      ansible.builtin.file:
        path: "{{ log_directory }}"
        state: directory
        owner: <MANAGED_USER>  # 디렉토리 소유자를 관리 계정으로 설정
        group: <MANAGED_GROUP>
        mode: '0755'

    - name: Install packages on RedHat
      ansible.builtin.dnf:
        name: "{{ item }}"
        state: present
      loop: "{{ packages }}"
      when: ansible_facts.os_family == "RedHat"

    - name: Install packages on Ubuntu
      ansible.builtin.apt:
        name: "{{ item }}"
        state: present
      loop: "{{ packages }}"
      when: ansible_facts.os_family == "Debian"

    - name: Monitoring dstat
      ansible.builtin.shell: |
        {{ item }} >> {{ log_directory }}/dstat.log
      loop:
        - dstat 2 10
        - dstat -cmdlt -D vda 2 10

    - name: Monitoring iostat
      ansible.builtin.shell: |
        {{ item }} >> {{ log_directory }}/iostat.log
      loop:
        - iostat
        - echo "==============="
        - iostat -t -c -dp vda
        - echo "==============="

    - name: Monitoring vmstat
      ansible.builtin.shell: |
        {{ item }} >> {{ log_directory }}/vmstat.log
      loop:
        - vmstat
        - echo "==============="
        - vmstat -dt
        - echo "==============="
        - vmstat -D
        - echo "==============="

    - name: Monitoring df
      ansible.builtin.shell: |
        df -h >> {{ log_directory }}/df.log

- 문법 체크: ansible-playbook -i inventory.ini --syntax-check monitoring_system.yml -K

- 실행 체크: ansible-playbook -i inventory.ini --check monitoring_system.yml -K

- 실행: ansible-playbook -i inventory.ini monitoring_system.yml -K

2.Container Infra Monitoring
1)전통적 방식과의 차이점
=>전통적 호스트 환경
- 고정 IP 체계: 장기간 불변하는 호스트 주소
- 정적 파일 설정: 파일을 직접 편집
- 설정 갱신 시 프로세스 재로딩 필요

=>동적 쿠버네티스 환경
- 단명성 워크로드: 수시로 생성 과 소멸을 반복하는 파드의 수명
- 가변 IP 주소: 재배포 될 때 마다 파드 IP 변경됨
- 자동화 필수: 선언적 리소스 탐색 컨트롤러 요구

2)컨테이너 인프라 환경의 모니터링
=>모니터링을 위한 3단계 구조
Master Node 와 Worker Node 모두에 node-exporter가 설치되서 수집된 메트릭을 통합하고 kubenetes 상태에 대한 메트릭스는 Master Node에서 kube-state-metrics가 통합을 하고 프로메테우스 대시보드나 그라파나 대시보드를 이용해서 시각화

=>모니터링 도구 선택
- 프로메테우스 와 그라파나는 오픈 소스 도구
- 오픈 소스는 가능한 한 단일 도구에서 단일 기능만을 구현하는 것을 선호
- 사용자 입장에서는 별도로 구현하기를 원하지 않기 때문에 기능을 모아서 한꺼번에 제공하는 것을 선호
- 프로메테우스 와 그라파나의 혼합 구조를 사용하는 이유
프로메테우스에 다른 시각화 도구를 연결하는 경우 라이선스 비용이 발생할 수 있음

서비스형 모니터링 도구들은 대부분 외부에 데이터를 저장해서 모니터링하게 되는데 이 경우는 보안에 민감해 지기 때문에 모든 데이터를 내부에서 처리하고자 하는 이유 때문에 프로메테우스를 직접 설치해서 사용

- Kibana
ElasticSearch를 개발한 Elastic에서 개발한 시각화 도구

Metricbeat를 이용하면 프로메테우스의 시계열 데이터를 ElasticSearch의 데이터로 변환이 가능

인플럭스DB만 사용이 가능

3)프로메테우스 모니터링 데이터 수집 과 통합
=>Prometheus Operator 패턴의 동작
- k8s API Server 상시 감시(CRD 변경 사항을 실시간 이벤트 감지)

- 선언적 설정 자동 생성(ConfigMap 내부 스크랩 구성 동적 변환)

- 무중단 설정 동기화(무중단 핫 리로드 API 호출 적용)

=>프로메테우스 오브젝트
- prometheus-server
프로메테우스의 주요 기능을 수행하는 요소
여러 대상에서 메트릭을 수집
시계열 데이터베이스를 소유
저장된 데이터를 질의하거나 수집 상태를 확인할 수 있는 UI 제공

- node-exporter
노드의 시스템 메트릭 정보를 수집해서 HTTP로 공개하는 역할
노드에서 특정 파일들을 읽고 프로메테우스 서버가 수집할 수 있는 형태로 변환하고 노드 익스포터에서 HTTP로 공개

- kube-state-metrics
API Server에서 여러 메트릭 정보를 수집해서 HTTP로 공개하는 역할
API Server에서 특정 파일들을 읽고 프로메테우스 서버가 수집할 수 있는 형태로 변환하고 노드 익스포터에서 HTTP로 공개

- alertmanager
경보 규칙을 설정하고 경보 이벤트가 발생하면 경보 메시지를 대상에게 전달하는 역할

- pushgateway
배치와 스케쥴 작업 시 수행되는 일회성 작업들의 상태를 저장하고 모아서 프로메테우스가 주기적으로 가져갈 수 있도록 공개
짧은 시간동안 실행되고 종료되는 배치성 프로그램의 데이터를 저장하거나 외부망에서 접근할 수 없는 내부 시스템의 메트릭을 프록시 형태로 제공
