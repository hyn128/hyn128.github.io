name: CI/CD Front App to AWS S3

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Code Checkout
        uses: actions/checkout@v3
      - name: AWS IAM User Config
        uses: aws-actions/configure-aws-credentials@v2
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ${{ secrets.AWS_REGION }}
    
      - name: React Build
        run: |
          npm install
          npm run build

      - name: S3 Upload
        run: aws s3 sync build/ s3://${{ secrets.AWS_S3_BUCKET }} --acl public-read
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}

3)Cloud Front
=>웹 페이지 호스트 와 네트워크 서버 설정을 위한 서비스
=>CDN
- Content Delivery Network는 리소스 요청이 발생했을 때 사요아작 현재 어디에서 요청하였는지에 다라 리소스를 전달해주는 분산 네트워크 시스템
- 목적은 Edge Location을 통해 사용자에게 최소한의 지연 시간과 최고의 성능으로 콘텐츠를 제공
최초로 웹 사이트 호스팅이 이루어지느 곳을 origin 이라고 하는데 이 웹 사이트는 전 세계 모든 지역에서 다양한 사용자가 방문

모든 지역에서 origin에게 요청을 해서 처리하는 경우 문제가 발생할 수 있음 - 멀리 떨어져 있으면 지연 시간이 발생

CDN은 많은 요청이 오가는 지역을 근거로 Edge Location을 생성

Edge Location은 Contents의 복사본을 가지고 있다가 근처의 사용자가 요청하면 Contents를 전송

동일한 요청을 자주 사용하는 애플리케이션은 CDN을 적극적으로 사용

정적 웹 사이트(클라이언트) 요청에 주로 사용: 서버는 대부분의 경우 데이터를 넘겨주는데 반해 클라이언트는 이미지 와 같은 실제 파일을 전송하기 때문에 클라이언트 애플리케이션에 더 중요

=>CloudFront가 AWS에서 제공하는 CDN 서비스로 데이터를 전송할 때만 과금

=>CloudFront 생성하면 도메인이 생성되는데 CloudFront 도메인으로 접속하면 CDN이 구현

=>CloudFront를 사용하는 경우 수정된 내용이 바로 적용되지 않는 경우가 발생
- CDN은 Edge Location에서 Caching을 수행
- 변경 내용이 Origin에는 적용이 되었는데 Edge Location에 적용되지 않는 경우가 발생
- 캐시 무력화 설정을 추가해야 합니다.

6.AWS Container Service
1)Container Service 
=>컨테이너 기술을 도입하기 위해서 고려해야 할 점
- 클라우드 서비스에서 컨테이너를 기반으로 플랫폼을 검토하는 경우 애플리케이션과 라이브러리의 의존 관계가 닫힌 상태로 여러 컨테이너가 연계하는 구성이 되므로 자연스럽게 분산 시스템과 같은 구성이 됨
- 분산 시스템을 전체로 한다면 컨테이너 간 느슨한 결합성 과 이식성을 고려한 방식을 검토해야 하고 컨테이너의 디스크 영역은 휘발성이어서 컨테이너의 파기와 동시에 내부의 데이터가 삭제되기 때문에 온프레미스 환경에서 서버를 다루는 경우와 다른 점
- 클라우드 서비스에서 컨테이너를 사용하기 애플리케이션 개발 방법론 중 하나가 The Twelve-Factor App(https://12factor.net/)

=>컨테이너 설계 및 운용에 관련된 자세
- 컨테이너 기술을 도입하면 당연히 그에 맞는 새로운 운용도 발생하는데 저장소에 저장된 이미지의 수명주기를 관리하거나 이미지를 보호해야 함
- 빌드에서 배포까지의 흐름과 컨테이너 오케스트레이션 자체의 권한 제어, 정의 관리, 보안 설계 등도 필요
- 클라우드 서비스를 이용하면 구축과 그 운용 부하는 일부 감소하지만 가용성과 운용성, 성능, 보안 등 기존 서버에서 필요했던 비기능 관련 부분은 변함없이 중요

2)AWS가 제공하는 컨테이너 서비스
=>Control Plane
- Amazon Elatic Container Service(ECS)
Fully Managed Container Orchestration
컨테이너를 관리해주는 서비스
컨테이너를 실행하지는 않음
AWS가 소유권을 가지고 있음
예전부터 사용해 와서 매우 많은 사용 사례를 가지고 있고 안정성을 가지고 있음

- Amazon Elastic Kubernetes Service(EKS)
완전 관리형 쿠버네티스 서비스
쿠버네티스 제어 플레인과 쿠버네티스 노드로 구성
쿠버네티스를 운용하는데 어려운 점은 제어 플레인을 건전하게 유지하는 것
EKS를 이용하면 쿠버네티스 제어 플레인 관리를 AWS에게 위임하는 것

=>Data Plane
- Amazon EC2
AWS에서 가상 머신을 이용할 수 있는 서비스

EC2는 ECS나 EKS에서 동작하는 컨테이너 데이터 플레인이 될 수 있음

EC2를 컨테이너 호스트로 이용하는 경우 호스트를 운영하는 비용은 높아짐

EC2를 사용하기 위한 자원을 할당하고 OS 업데이트 와 보안 패치 적용, 서버가 제대로 작동하는지 확인하기 위한 모니터링 등 안전하게 자원을 관리할 책이 부과 되기 때문

사용자의 요건에 맞는 설계가 가능하기 때문에 유연성을 요하는 설계가 필요한 경우에는 EC2를 데이터 플레인을 선택하기도 함

- Fargate
ECS 와 EKS에서 모두 사용 가능한 컨테이너용 서버리스 컴퓨팅 엔진으로 AWS의 완전 관리형 데이터 플레인
컨테이너용 이므로 ECS 또는 EKS 와 함께 사용
장점
	호스트를 관리하지 않아도 되기 때문에 서버 확장, 패치 적용, 보호, 관리와 같은 운용 오버헤드는 전혀 발생하지 않음
	컨테이너 실행 환경은 AWS에서 언제나 최신 상태를 유지
단점
	EC2를 사용하는 것 보다 비쌈
	AWS에서 컨테이너 실행을 위한 OS를 관리하기 때문에 커널 관련 매개변수와 같은 데이터 플레인 측 OS 자원을 세세하게 튜닝하는 애플리케이션과는 맞지 않음
	CPU/메모리 할당에 제한이 있으며 컨테이너 기동 시간이 다소 오래 걸림

Fragate Scaling은 매우 단순

OS를 직접 관리하지 않기 때문에 전담 인력을 충원할 필요가 없기 때문에 실제 과금은 EC2가 더 저렴하지만 TCO(Total Cost of Ownership - 처음 사는 가격이 아니라 쓰는 동안 들어가는 돈까지 다 합쳐서 판단하자는 관점) 관점으로 보면 Fargate가 압도적으로 유리

비즈니스에서 부가 가치를 만드는 활동에 주력하는 의미에서도 신규 컨테이너를 구축할 때는 Fargate 활용이 가능한지 적극적으로 검토

=>Image Repository
- Amazon Elastic Container Registry(ECR)
완전 관리형 컨테이너 저장소
컨테이너 이미지를 간단하게 저장하고 관리
ECS 와 연계가 쉽기 때문에 컨테이너를 만들 때도 간단히 ECR에 저장된 컨테이너 이미지를 가져올 수 있음
AWS에 시스템에 구축할 때 AWS의 다른 서비스와의 연계나 보안 설정 등을 생각해보면 ECR을 사용하는 것을 추천

4)기타 관련된 내용
=>AWS Lambda
- 이용자가 소스 코드를 업로드하는 것 만으로 애플리케이션을 실행할 수 있는 서비스
- AWS가 제공하는 컴퓨팅 자원을 인프라로 활용해 자동으로 애플리케이션 서버를 구축해주는 완전 관리형 서비스
- Firecracker라는 컨테이너에서 실행되며 경량 마이크로 가상 머신을 실행
- 람다도 컨테이너 기술을 사용하는데 서버리스라는 관점에서 보면 Fargate도 같은 의미를 가지지만 람다는 개발자가 컨테이너 기술에 신경 쓸 필요없이 개발에만 집중하게 해준다는 점이 다름
- 데이터 플레인을 고려하지 않아도 되므로 ECS 나 EKS같은 제어 플레인을 배치할 수 없음
- ECS 나 EKS를 사용하지 않고 람다만으로 서비스를 개발하면 관리할 부준을 최소화 할 수 있음
- 소스 코드 와 할당 메모리 그리고 실행을 위한 IAM 권한만 관리하면 부담을 줄일 수 있음
- 람다에서 구현할 수 없는 애플리케이션이라면 ECS 나 EKS 아니면 EC를 사용하는 방법을 고려
- 이 방식은 AWS에서 관리하는 EC2에서 실행하는 방법과 Firecracker에서 실행하는 경우가 있는 사용자는 알 필요가 없음

=>App Runner
- 애플리케이션을 빠르게 구축하고 배포할 수 있게 해주는 완전 관리형 서비스
- Git Hub와 연동해서 소스 코드를 앱 러너에서 빌드 및 배포할 수 있을 뿐 아니라 ECR의 빌드된 이미지도 바로 배포할 수 있음
- 애플리케이션 개발자가 보다 간단하게 웹 애플리케이션을 배포할 수 있게 하는데 주안점을 둠
- ECS 와 Fargate로 애플리케이션을 구축할려면 네트워크 나 로드밸런싱 그리고 CI/CD 설계와 같은 인프라 설계를 해야 하므로 인프라 관련 지식이 어느 정도 필요
App Runner는 인프라 관련 구축을 모두 블랙박스화해서 관리할 수 있게 해줌
- 이슈도 잘 관리되고 개선되고 있어서 요건에 맞게 사용하면 강력한 솔루션

=>ECS on EC2
- Control Plane이 ECS 이고 Data Plane이 EC2 인 경우

- EC2에 ECS 태스크를 실행해 태스크 위에서 컨테이너를 가동시키는 방식

- 비용
EC2 인스턴스와 EBS 볼륨에 대한 서비스 이용 요금이 발생
너무 작은 인스턴스를 선택하면 ECS에서 배치하는 태스크를 확장할 수 없음
유지보수 비용이 많이 듬
온프레미스 경험과 검색을 통해서 많은 정보를 얻을 수 잇기 때문에 학습 비용은 낮음

- 확장성
EC2는 이미지 캐시를 이용하기 때문에 배포의 신속성은 우수
수평 스케일링은 용량 계획을 얼마나 잘 세웠느냐에 따라 영향을 받기 때문에 다소 약한 편인데 확보한 용량까지만 스케일링이 가능
자원 확장은 우수한데 EC2 사양은 AWS 관리 콘솔에서 클릭 몇 번으로 변경이 가능

- 신뢰성
장애 복구 측면에서 보면 ECS는 관리형 서비스이므로 장애 복구는 AWS의 책임
EC2에 문제가 발생하면 SSH로 서버에 로그인해서 원인을 조사하는데 최근에는 Systems Manager를 사용해 SSH를 사용하지 않고도 서버에 로그인 할 수 있음
ECS에 문제가 생겼을 때 지원은 좋은 편
ECS는 AWS 자체의 오케스트레이터이며 내부 동작도 모두 AWS에서 설계한 것이므로 지원 요청을 하면 공개된 정보인 경우 내부 사양 과 설계에 대한 조언도 받을 수 있기 때문에 전문적인 지원을 기대할 수 있음

- 엔지니어링 관점
엔지니어의 수가 많은 편

=>ECS on Fargate
- Control Plane은 ECS이고 Data Plane은 Fargate인 아키텍쳐
- Fargate의 ECS 태스크를 실행해서 태스크 위에 컨테이너를 가동시키는 것
- 비용
Fargate 비용이 거의 대부분
vCPU 와 메모리 자원은 컨테이너 이미지를 취득한 시점부터 ECS 태스크가 종료될 때 까지를 계산해서 초 단위로 과금하지만 최저 요금은 1분 경과 후의 요금
EC2에 비해서 과금은 많이 되지만 운용 비용이 낮은데 인프라 관리 비용이 들지 않음: TCO 관점에서 유리
컴플라이언스 준수 관점에서도 가치가 있는데 ECS/Fargate는 신용 카드 업계의 정보 보안 기준인 PCI DSS를 준수
학습 비용이 낮음
- 확장성
배포의 신속성은 우수하지 않음
Fargate는 컨테이너 별로 ENI(Elastic Network Interface)를 연결해야 하기 때문에 ENI 생성이 시간이 걸림
Fargate는 이미지 캐시를 활용할 수 없음
수평적 확장은 Fargate가 쉽게 조절
자원 확장에는 제한이 있음
작업에 할당되는 휘발성 스토리지는 200GB 인데 영구 스토리지 용량은 필요한 경우 EFS 볼륨을 활용할 수 있기 때문에 강한 제약은 아님
할당 가능한 자원이 4vCPU, 30GB 메모리가 최대이므로 머신 러닝에 사용하는 노드의 경우 적합하지 않음
- 신뢰성
ECS와 관련한 부분은 ECS on EC2와 동일
Fargate는 AWS가 관리하는 호스트라서 SSH를 통해 호스트에 접근할 수 없음
컨테이너에 sshd를 실행해서 컨테이너에 직접 로그인하는 방법을 사용할 수 있으나 보안상 컨테이너에 직접 로그인 하는 것은 권장하지 않음
AWS가 대부분을 관리하기 때문에 다양한 지원이 가능
- 엔지니어링 관점
엔지니어 확보는 쉬운 편

=>EKS on EC2
- 비용
EKS에서도 비용 발생
EKS 비용은 Data Plane 비용에 비하면 적은 편
쿠버네티스는 약 3개월에 한 번씩 마이너 버전이 나오는데 EKS에도 이 특징은 계승되며 EKS의 마이너 버전은 출시 12개월간 지원
3개월에 한 번씩 애플리케이션이 제대로 동작하는지 확인
학습 비용은 비교적 높은 편

- 확장성은 ECS on EC2와 거의 차이가 없음

- 신뢰성
EKS도 관리형 서비스이기 때문에 EKS 자체의 장애나 물리 장치의 고장은 AWS가 책임지고 관리하지만 쿠버네티스의 장애는 직접 해결

- 엔지니어링 측면
ECS 보다는 개발자를 구하는 것이 어려움

=>EKS on Fargate
- Pod 와 Node의 관계
하나의 노드에는 여러 개의 Pod가 배치될 수 있는데 EKS on Fargate에서는 하나의 노드에 1개의 pod 만을 배치할 수 있음
DaemonSet을 사용할 수 없음
DaemonSet을 사용하고자 하는 경우에는 Pod 안에 사이드카 컨테이너를 별도로 구축해 데몬을 실행

- 클러스터 외부로부터의 통신이 가능한 로드밸런서
EKS의 엔트포인트를 클러스터 외부에 공개할 때 로드밸런서를 사용
사용할 수 있는 로드밸런서는 Service(CLB, NLB, ALB) 와 Ingress(AWS Load Balancer Controller, NLB)를 로드밸런서로 사용하는 것이 가능

- 비용
가장 많은 비용이 부과
운용 비용은 줄어듬: Fargate는 버전업 작업이 불필요

- 확장성은 ECS on Fargate와 큰 차이가 없음

- 신뢰성은 EKS on EC2와 같음

- 엔지니어링 관점에서 보면 ECS 보다 개발자를 구하기가 어려움

6)아키텍쳐 적용 사례
=>온프레미스 또는 EC2에 쿠버네티스를 사용하는 경우
- 직접 쿠버네티스의 제어 플레인 및 데이터 플레인을 운영하는 경우
- 보안이나 비용 때문에 사용

=>블록 체인을 이용하는 Full Nodes를 구축하는 경우
- 블록 체인은 3가지 역할로 구분
Full Node
Validator(검증자)
Miner(채굴자)
- Full Node는 노드에 존재하는 모든 블록을 가지고 있기 때문에 대용량 데이터를 로컬에 저장하고 있어야 함
- Data Plane으로 디스크 용량을 무한대로 가질 수 있는 EC2를 사용
- Control Plane은 ECS를 권장

=>머신러닝을 수행해야 하는 경우
- Fargate는 GPU 사용을 못함
- Data Plane으로 GPU 사용이 가능한 EC2를 사용
- Control Plane은 ECS를 권장

=>높은 자원 집약율을 실현하고자 하는 경우
- CPU나 메모리를 낭비하지 않는 경우
- 온프레미스에서는 CPU 나 Memory를 100% 가깝게 사용하면 시스템이 다운되거나 커널 패닉이 발생할 수 있음
- 퍼블릭 클라우드에서는 자원을 100%에 가깝게 사용하는 것이 비용 효율이 좋음
- EC2는 매번 인스턴스 사양을 변경하면서 사용해야 자원 집약율을 높일 수 있지만 Fargate 인스턴스 유형을 선택하지 않아도 되므로 CPU 와 메모리 요건을 지정해서 호스트를 만들고 컨테이너를 실행하면 됨
- 자원 집약율을 높이고 싶으면 Fargate를 권장
