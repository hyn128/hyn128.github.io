- snapshot
어떤 시점의 디스크 상태를 보존한 파일이나 디렉토리의 집합
디스크의 전체를 보존하기 때문에 데이터나 소프트웨어 뿐 아니라 OS 와 설정 정보등도 모두 포함
백업의 용도도 있고 AWS에서는 AMI를 만들기 위해서 스냅샷을 사용하기도 함
AWS에서는 처음에는 디스크 전체를 보존하지만 두번째 이후에는 증분(변경된 내용)된 내용만 보존
삭제를 하면 변경되지 않은 부분은 다음 스냅샷에 합친 후 삭제
스냅샷은 특정 시점의 상태
관리 콘솔에서 볼륨 단위로 선택하여 생성
스냅샷을 기반으로 EBS 볼륨을 생성하면 새로운 볼륨은 원래 볼륨의 복제
AWS에서는 데이터 수명 주기 관리자(Amazon DLM)을 이용하면 스냅샷의 생성 및 삭제를 자동화 할 수 있음
요금은 스냅샷의 분량 단위(GB)로 발생
실제 보존 장소는 S3이지만 사용자가 자유롭게 다운로드 할 수 없음

- Auto Scaling의 한계
갑자기 트래픽이 증가하면 전체 시스템에 장애가 발생: 오토 스케일링이 동작해서 인스턴스를 생성하는 속도보다 트래픽이 더 빨리 증가하는 경우
오토 스케일링은 트래픽이 점진적으로 증가하는 경우에 적합
갑자기 폭주하는 트래픽이 예상되는 경우에는 미리 인스턴스를 생성해야 함

- AWS에서 오토 스케일링을 설정하는 방법
동적 크기 조정 정책 생성: 점진적으로 증가하는 트래픽에 적합
예약된 작업: 특정 시간에 맞춰 인스턴스를 생성해 놓는 방법
예측 크기 조정 정책: 일정한 패턴으로 들어오는 트래픽이 있다면 며칠동안 오토 스케일링을 교육시키고 그 이후로 예측되는 트래픽에 맞춰 미리 인스턴스를 만들어 놓는 방법

2)Amazon RDS
=>개요
- 관계형 데이터베이스를 클라우드에 최적화된 상태로 제공하는 서비스
- Amazon Aurora 이외에 PostgreSQL, MySQL, MariaDB, Oracle Databae, MS SQL Server, IBM DB2를 지원
- Aurora 버전은 기존 소스들을 AWS에 맞게 수정한 버전
- 데이터베이스 제공 방식은 EC2와 비슷한데 VPC 상에 인스턴스 형태로 구축하며 다양한 인스턴스 클래스를 사용할 수 있음
- EC2 와 다른 점은 Managed Service 라서 업데이트 등의 관리를 AWS가 담당
- AWS database Migration Server를 사용하면 기존 데이터베이스를 이전하거나 복제하는 것도 가능

=>인스턴스 클래스
- EC2 와 마찬가지로 인스턴스 형식으로 사용
- 인스턴스 크래스는 표준, 메모리 최적화, 버스트 성능의 3종류가 있으며 클래스에 따라 micro, small, medium, large, xlarge, 2xlarge, 4xlarge, 8xlarge, 16xlarge 크기를 제공하는데 인스턴스 클래스에 따라 지원하지 않는 DBMS나 버전도 있음
- 표준은 m으로 시작하는 범용적인 인스턴스 클래스
- 메모리 최적화는 x1e, x1, r5 등이 있음
- 버스트 성능은 t3가 있는데 CPU의 최대 사용률까지 버스트 성능으로 사용할 수 있음

=>요금 체계
스토리지 요금
데이터베이스 인스턴스 구동 시간
백업 스토리지: 스냅샷에 부과되는 요금으로 데이터베이스 스토리지 크기의 100%가 넘는 경우에만 부과
통신료(동일한 VPC 내의 EC2  인스턴스와 통신하는 경우는 부과되지 않음)

=>장점
Managed Service
간단하게 데이터베이스를 생성할 수 있으며 On-Premise에서 데이터를 이전하기 쉬움
EC2와 연동하기 쉽고 동일한 네트워크 안에 존재하면 통신료도 무료

=>단점
사용자가 자유롭게 사용할 수 없음: DBMS 종류나 버전이 한정되어 있음
AWS가 업데이트를 자동으로 수행해서 편리하지만 오히려 업데이트하면 곤란한 시점에 수행될 수 있음

=>지원하는 데이터베이스
- Aurora: MySQL 과 PostgreSQL과 호환이 가능한데 AWS가 만든 관계형 데이터베이스
- 요금이 비싼반면 견고하고 성능이 뛰어남
- AWS 용으로 설계가 되서 일반적인 MySQL 이나 PostgreSQL 보다 속도가 빠르고 Managed Service 라서 안전하게 사용할 수 있음
- S3로부터 복제를 수행하는 경우 가용 영역 여러 개를 이용해서 다중화한다면 일반적인 MySQL 이나 Postgre SQL은 하나의 영역에 복제본을 만들고 그 복제본을 이용해서 다른 가용 영역에 복제를 수행합니다.
Aurora를 이용하면 병렬로 복제를 수행
- 많은 DML을 수행하는 경우 훨씬 적은 Replica로 처리가 가능
